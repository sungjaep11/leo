공유 경로 예측 캐시를 이용한 Vegas — 2026-10-09
==============================================

구현한 구조
같은 ns-3 프로세스의 main_satnet에 별도 예측 모듈을 두었다.
이 모듈은 현재 위성/지상국 위치, 현재 양방향 전달 경로, 링크 속도로
큐가 없을 때의 데이터+ACK 왕복 시간을 주기적으로 계산한다.
같은 source/destination 쌍의 TCP 연결은 하나의 예측 이력을 공유한다.
TCP는 각 RTT 표본 처리 시 저장된 값만 조회하며 궤도/경로 계산을 하지 않는다.

알고리즘과 가정
1. P = 각 링크 거리 / 해당 채널 전파 속도의 왕복 합.
2. S = 각 링크의 패킷 전송 시간 합. 데이터 1434, ACK 54바이트:
   MSS 1380 + TCP 타임스탬프 헤더 32 + IPv4 20 + PPP 2에 맞춘 모델.
3. 예측 무부하 RTT = P+S. 주기 기본값 100ms, 이전 계산값을 유지하는 방식.
   계산 시점의 위치와 현재 경로를 쓰는 snapshot 근사이다.
   홉마다 미래 도착 시각의 위치/경로를 다시 계산하는 정밀 모델은 아니다.
   미래 fstate를 읽거나 현재 경로를 새로 탐색하지 않는다.
4. TCP의 ACK 도착 시각에서 실제 RTT 표본을 빼서 전송 시각을 추정한다.
   TCP 타임스탬프 정밀도에 따른 오차가 있다.
   그 전송 시점까지 사용 가능했던 가장 최근 예측값을 조회한다.
5. TCP와 동일한 RttEstimator 설정을 복제하여 예측 RTT도 평활화한다.
   Vegas가 주기 minRTT로 고른 관측값과 짝이 되는 평활 예측값을 사용한다.
6. baseRTT = min(해당 평활 예측값, Vegas 주기 minRTT).
   모델과 측정 양자화의 차이로 base>min이 되지 않게 하는 제한이다.
   예측값보다 큰 큐 지연을 기준값에 흡수하지 않는다.
7. 기존 cwnd 조절, alpha/beta/gamma, 재전송 복구 규칙은 유지한다.
   시작부터 활성화한다. 알려진 경로 변경 시각을 하드코딩하지 않는다.

앞서 논의한 anchor+전파시간 변화량 방식을 그대로 구현한 것은 아니다.
링크 전송시간까지 모델에 포함하여 절대 무부하 RTT 예측값으로 기준을 설정한다.
무부하 UDP 측정값이나 실제 큐 길이는 제어 알고리즘에 제공하지 않는다.
이전 UDP 측정 결과는 analyze.py에서 오차 평가에만 사용한다.

배치 가정
현재 라우팅과 위치 정보에 이상적으로 접근하는 network-assisted 모듈이다.
실제 송신자가 이 정보를 원래 알고 있다는 뜻은 아니다.
기본값은 정보 즉시 전달이며, 100/500ms 늦게 제공되는 경우도 별도로 실행했다.
정보 전달 패킷의 대역폭/손실/보안, 경로 생성 자체의 비용은 구현하지 않았다.
위치 오차와 경로 예측 오차도 아직 별도로 주입하지 않았다.

공유와 저장
키: (송신 노드, 수신 IP). 값: 계산/사용가능 시각, 경로 ID, 예측 RTT.
최근 약 10초와 전달 지연을 커버하는 이력을 보존한다.
100ms 갱신, 전달 지연 0에서 최대 이력 항목은 경로당 102개였다.
조회는 이력에서 사용가능 시각에 대한 이진 검색이다.
같은 경로의 연결 2개를 5초 실행하여 등록 2회, 캐시 1개, 계산 50회를 검증했다.
경쟁 트래픽 유무 및 ACK 동작을 바꿔도 동일한 지형/경로의 예측값은 동일했다.

주요 결과: 원래 이동 경로, 121.6~200초
방식                 ACKed 전송률  단일 큐 최대  개별 큐 최대 대기
기존 Vegas            27.83 Mbps       5           0.459 ms
최근 5초 최소 RTT     83.39 Mbps      14           1.533 ms  (이전 실험)
공유 예측 캐시 100ms  89.13 Mbps       5           0.459 ms
100ms 버전의 170~185초: 96.232 Mbps; 195~200초: 77.276 Mbps.
121.6초 이후 Vegas diff>beta에 의한 감소는 기존 550회, 100ms 버전 0회.
경로 변경 직후의 재전송 복구는 남아 있다.

갱신 주기/정보 지연 민감도: 121.6~200초 ACKed 전송률
10ms 갱신: 89.12; 100ms 갱신: 89.13; 500ms 갱신: 88.98 Mbps.
100ms 갱신 + 100ms 전달 지연: 89.10 Mbps.
100ms 갱신 + 500ms 전달 지연: 88.72 Mbps.
한 경로/seed에서 얻은 결과이며 일반적인 최적 갱신 주기 증명은 아니다.

계산 비용: 100ms 갱신, 200초 모의 실행
예측 계산 2,000회, 캐시 조회 651,298회, 캐시 미스 0회.
예측 계산 평균 약 45.35마이크로초, 조회 평균 약 0.127마이크로초.
예측 계산 계측 합계 0.0907초, 조회 계측 합계 0.0824초, 둘을 합해 0.1731초.
10ms 갱신은 계산 20,000회, 합계 0.9498초였다.
주의: steady_clock으로 잰 해당 코드 구간의 wall time 합계이다.
로그 기록, 초기화, 연결별 RTT 평활화 및 실제 네트워크 정보 전달 비용은 제외된다.
동시 실행/호스트 스케줄링과 계측 자체의 영향이 있어 정밀한 CPU 벤치마크는 아니다.
전체 시뮬레이션 시간 차이를 모듈의 오버헤드로 해석하면 안 된다.
트래픽 양이 다른 실행들끼리 전체 실행 시간을 직접 비교하지 않았다.

예측 오차: 이전 독립 무부하 프로브와 사후 비교
100ms 캐시의 평균 절대 오차 0.00673ms, 95백분위 0.00445ms.
그러나 경로 전환/이동 중인 패킷의 경로 변화 구간은 최대 약 7.97ms 오차.
평균 오차만으로 경로 전환 순간에도 정밀하다고 주장할 수 없다.

경쟁 부하 검증
A. 이동 경로 + 130~180초 80Mbps UDP:
170~180초 기존 2.89Mbps, 100ms 예측 버전 19.14Mbps.
같은 조건의 이전 최근-5초 방식은 19.15Mbps, 큐 최대 38패킷/대기 4.414ms.
예측 버전은 큐 최대 7패킷/대기 0.737ms였다.
즉 비슷한 전송률에서 큐 증가를 더 작게 유지했다.

B. 위치/경로 고정 + 60~100초 80Mbps UDP:
예측 RTT는 부하와 무관하게 99.787733ms로 일정했다.
하지만 부하 시작 후 복구 과정에서 작은 cwnd에 머무는 실패 사례가 있었다.
90~100초 기존 6.18Mbps, 예측 버전 1.55Mbps. 이 결과를 숨기면 안 된다.
예측 버전의 cwnd는 15세그먼트, cycle min(SRTT)는 약 109.5ms였다.
같은 구간 개별 큐 대기는 최대 약 0.282ms라서 전파/큐 보정만으로 설명되지 않는다.
지연 ACK/SRTT/작은 윈도와 복구의 상호작용에 대한 추가 개선이 필요하다.

별도 진단: ACK를 매 세그먼트마다 보내도록 DelAckCount=1로 변경
90~100초 17.12Mbps로 회복했지만, 앞부분의 손실·복구 진동도 달라졌다.
ACK 설정은 시작부터 변경했으므로 부하 직전 상태가 같은 단일 시점 개입은 아니다.
ACK 처리와의 상호작용을 시사하지만 원인 하나를 확정하는 실험은 아니다.
이 진단을 기본 알고리즘의 성능으로 보고하지 않는다.

드롭 관측 보완
기존 Queue::Drop 외에 TrafficControlLayer::TcDrop를 추가 기록했다.
고정 경로의 예측 버전 전체 실행에서 TcDrop 783회가 관측됐다.
장치 큐가 멈춘 경우 장치 큐에 들어오기 전에 버려져 기존 큐 Drop에는 안 잡힐 수 있다.
이동 경로+부하에서는 기존 782회, 예측 버전 1,020회 (주로 부하 시작 과도 구간).
따라서 정상 구간의 큐 개선이 과도 구간 손실까지 해결했다는 뜻은 아니다.

검증
- 기능을 끈 전체 200초 cwnd/RTT/progress가 원래 Vegas와 바이트 단위 동일.
- 모든 본 실험과 진단 finished=Yes 확인.
- 모든 기준 RTT 적용 로그의 예측 생성/사용가능 시각이 전송 추정 시각 이하.
- 적용된 baseRTT와 예측/관측 상한 관계를 검사.
- 같은 시나리오의 config와 TCP 스케줄이 동일.
- 실제 경쟁 트래픽/ACK 동작에 모델 예측값이 영향을 받지 않음을 검사.
- 두 연결의 캐시 공유 검사, 설치 파일 해시 검사.
